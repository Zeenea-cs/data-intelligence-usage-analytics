Overview

Catalog activity, without the manual export

Governance and data teams want to see who's documenting what, and how that changes over time. Today that means logging into three different APIs and stitching CSVs together by hand.

  • The Actian Data Intelligence Platform holds this data across four separate interfaces: the Audit API, the Catalog API, the User Management API, and SCIM, with no single place to query or trend it.
  • This companion collects all four on a schedule, stores the result in PostgreSQL, and exposes it through Metabase so anyone can self-serve a report instead of asking an engineer for a query.
  • Answers questions like: who are the most active curators, which items get modified most, how is documentation coverage trending, and how many licensed stewards vs. explorers do we have.
Overview

Four services, one docker compose up

db

PostgreSQL 16. The companion's own database, actian_companion, holding every collected row.

collector

Python 3.12. Pulls Audit / Catalog / User Management / SCIM data on a cron, upserts it into Postgres, and serves a small trigger web UI on port 8000.

metabase

Metabase (open source). Dashboards and self-service exploration on port 3000.

metabase-db

A second PostgreSQL instance for Metabase's own application data, kept separate from actian_companion on purpose.

Architecture

What happens on every run

1
Trigger
cron schedule, container startup, or a click in the web UI
→
2
Collect users
User Mgmt export + SCIM, upsert into users
→
3
Collect audit events
incremental since the last successful run, upsert into audit_events
→
4
Collect items
enrich from Catalog API for every item seen in the audit trail
→
5
Record the run
one row in collection_runs: success, partial, or failed

If one collector fails, the run is marked partial and the rest continue: a bad audit fetch never stops user collection, and never crashes the scheduler.

Data model

Five tables, one source of truth

users

One live row per person, upserted.

  • is_steward
  • roles (jsonb)
  • email

audit_events

Item-level activity, deduped by event id.

  • event_id (unique)
  • action, item_id
  • occurred_at
  • actor_id (incl. former users)

items

Catalog objects referenced by audit events.

  • item_type
  • owner_id
  • last_updated_at

collection_runs

One row per cycle: the operational log.

  • status
  • users / events / items collected

user_snapshots

Append-only. One row per user, per run, never updated, so licence use can be trended over time.

  • snapshot_at
  • license_type

Get it running: Prerequisites

Before you start

  • Docker Engine 24 or later.
  • Docker Compose v2 (the docker compose ... form, not the old docker-compose binary).
  • A valid Actian / Zeenea instance URL and API key, with read access to the Audit, Catalog, User Management and SCIM APIs.
  • Python on the host is not required: everything runs in containers. It's only needed if you want to run the Metabase setup script by hand instead of letting the stack run it for you.
Setup: Step 1 of 5

Clone the repo, then configure

git clone https://github.com/Zeenea-cs/data-intelligence-usage-analytics.git
cd data-intelligence-usage-analytics/actian-companion
cp .env.example .env

Edit .env and set the four values with no working default:

ACTIAN_INSTANCE_URL

Full base URL, no trailing slash.

ACTIAN_API_KEY

Sent as X-API-SECRET. Treat as a secret.

POSTGRES_PASSWORD

Companion database password.

METABASE_DB_PASSWORD

Metabase's own application database password.

⚠
Also set a strong METABASE_ADMIN_PASSWORD: Metabase rejects common or short passwords, which would fail the automatic dashboard setup.
Setup: Step 2 of 5

Prepare logs, then start the stack

# every service writes its logs here - open perms let the
# Postgres / Metabase container users write to it
mkdir -p logs && chmod 777 logs

docker compose up -d

That's it. Four containers start: db, collector, metabase, metabase-db, plus a one-shot metabase-setup job.

Setup: Step 3 of 5

Watch it come up

docker compose ps
docker compose logs -f collector   # Ctrl-C to stop following
  • Postgres and the collector are ready in seconds; Metabase takes 1–2 minutes on its first boot.
  • On startup the collector runs its database migrations automatically, then performs one immediate collection so the database isn't empty, and from then on runs on the configured schedule.
  • The metabase-setup job waits for Metabase to be healthy, connects the database, and builds the dashboards: watch it with docker compose logs metabase-setup. It's idempotent, so re-running it is always safe.
Setup: Step 4 of 5

Open Metabase

Once healthy, the dashboards are waiting at:

http://localhost:3000

Default admin login, unless overridden in .env:

email

admin@actian-companion.local

password

Actian-Companion-2026!

⚠
Change METABASE_ADMIN_PASSWORD in .env before running this anywhere other than your own machine.
Setup: Step 5 of 5

Trigger a manual run

No need to wait for the cron: the collector serves a small web UI at http://localhost:8000.

Run collection now

Incremental: audit events since the last successful run. Upserts new and changed data; nothing is deleted.

Force reload historydestructive

Deletes all collected users, items and audit events, then rebuilds from scratch over the window you choose. Asks for confirmation in the UI.

curl -X POST http://localhost:8000/api/collect   # 202 started, 409 if already running

Scope

Known limitations

  • Only eventType = Item audit events are collected: User, Group, ApiKey and PermissionSet audit events are not stored.
  • Item enrichment depends on the Catalog API and only covers items actually seen in the audit trail; items deleted from the catalog are skipped and re-checked on later runs.
  • Steward detection is based on the User Management export's License type == "Steward", not a SCIM group name.
  • This is a single-tenant tool built for one Actian instance at a time, not designed for high-volume or high-availability deployment.
